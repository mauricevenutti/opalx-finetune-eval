Training data (catalog.py, questions.py; the composition groups of experiment 04 are in experiments/04/compositions.py)

task_type What it is Topics per question
recall Short factual question with a concise answer; 4 wordings per topic share one answer 1
mechanism "How/why does it work" question with a longer connected explanation of the implementation; 4 wordings per topic share one answer 1
scenario Concrete what-if or contrast situation ("NX is changed after building, what happens?"); 2 per topic, each with its own answer 1
composition Broad question over a group of related topics, often a concrete situation; the answer is the topics' mechanism answers joined verbatim. 4 questions per group, sharing one answer (only experiment 04, experiments/04/compositions.py) 2–4

Composition rows (experiment 04, experiments/04/build.py):

  1. Groups chosen by hand (experiments/04/compositions.py, GROUPS): related topics of the catalog, each group with a name, a short description of its area (scope) and 2–4 topics. The groups are not the 39 topics (TOPICS in catalog.py): a group combines several of them, a topic can be in several groups (each of the 39 is in 1–5). There were also 39 groups before the benchmark filter (step 2), but the two counts are unrelated. Example: ('borrowed_access', 'borrowed particle resources, per-call activity storage, and migration invalidation', ['algorithm_ownership', 'context_lifetime', 'migration_views']).
  2. No overlap with the benchmark: of the 39 groups first written, those whose topic set equals the topic set of a multi-topic eval, test or demo question were removed (resource_layers = eval-042, source_plane_resolution, time_dependent_passes; listed in EXCLUDED), leaving 36. build.py asserts that no kept group matches such a topic set and that no question equals a benchmark question. It reads only the benchmark questions and topic sets, never the reference answers.
  3. Answer: for each topic of the group, its mechanism answer (read from experiments/02/train.jsonl), joined verbatim and in group order with blank lines. No new text, no transitions. Individual facts and smaller topic subsets of the benchmark combinations do overlap, on purpose.
  4. Questions: 4 per group (144 in total), written one by one by hand, often as a concrete situation, e.g. for setup_snapshot: "A command executes successfully, and someone then changes its mesh attributes. Explain which configuration is validated, which values the running solver sees, and how that solver was connected to tracking." They replaced generic templates (STEMS, e.g. "Walk me through {scope} in OPALX. ..."); the template version is kept as parent_question in the metadata.

Only test.jsonl is truly held out.

Judge

scripts/judge.py (called by scripts/report.sh) grades all checkpoints of one run in a single call to Claude Opus 5.5 (claude -p on the Claude subscription, effort high by default). The call contains:

  1. a short role prompt (expert OPALX reviewer) and scripts/JUDGE.md as the grading rules,
  2. the 20 pinned OPALX source excerpts (data/evidence/excerpts.jsonl, commit b5f495e) as the source of truth; a copy is written to experiments/sources/ (gitignored),
  3. for each of the 48 eval questions: the question, the reference answer, the numbered required claims (R1, R2, ...) and forbidden claims (F1, ...) from data/eval.jsonl, followed by the fine-tuned answer of every checkpoint.

Blinding: the answers of one question appear under shuffled labels (A, B, ...), so the judge does not know which checkpoint wrote which answer, and it is told to grade each answer on its own, not relative to the others. It never sees base-model answers, checkpoint names, training data or hyperparameters. The answers come from greedy decoding with at most 768 new tokens (scripts/evaluate.py; --temperature samples instead, and --out writes the answers to another run folder, as in experiment 02b).

The output is forced into a JSON schema. judge.py rejects the whole response (and writes nothing) unless every (question, checkpoint) pair is judged exactly once and every list has one entry per claim. One exception: a forbidden_present list that is too long but all false (seen once on the demo) is cut to length and listed under repairs in the meta file. Before the call, judge.py writes judgments_<split>.call.json (label seed, checkpoints, model, effort, prompt hash); after a rejected response and a fix to judge.py, judge.py --run <run> --split <split> --from-raw evaluates the saved .raw.json again without a new Claude call. It refuses if the rebuilt prompt differs from the one sent.

Per answer (one row in runs/<exp>/<jobid>/judgments_eval.jsonl)

Set by the judge, following JUDGE.md:

Field Meaning
required_met one true/false per required claim, in order. True only if the answer actually conveys the claim; equivalent wording counts, naming a symbol without the required relationship does not
forbidden_present one true/false per forbidden claim. True only if the answer asserts that wrong claim; correctly negating it is fine
other_material_error true for any further materially wrong, unsupported, contradictory or overconfident claim about the repository, including an invented reason for a correct conclusion
certainty the judge's confidence in this judgment: high, medium or low
rationale short explanation of missing facts and errors

Derived by judge.py from these fields (no further model call):

Field Formula
material_error any(forbidden_present) or other_material_error
fully_correct all(required_met) and not material_error: the primary metric
claim_fraction sum(required_met) / len(required_met): share of required claims covered

Each row also carries step, checkpoint, the question's category, task_type and topics, finetuned_truncated (the answer hit the 768-token limit without ending) and answer_sha256. An empty answer meets no claims and has no material error, so it is never fully correct.

Per checkpoint (printed table, judgments_eval.meta.json, plots)

Metric Formula Better
fully correct number (and %) of the 48 answers with fully_correct higher
mean claim coverage mean of claim_fraction over the 48 answers (each question weighs the same, regardless of its number of claims) higher
material errors number (and %) of answers with material_error lower
truncated number of answers that hit the token limit lower

Best checkpoint: most fully correct answers; ties go to higher mean claim coverage, then fewer material errors, then the earlier step. judge.py and scripts/analyze.py use the same rule.

judgments_eval.meta.json also records the model, effort, SHA-256 of the prompt, JUDGE.md and the excerpts, token usage, and reference_issues: questions whose reference answer or claims the judge found to contradict the source. These are listed, not removed; decide by hand whether to exclude them from all runs.

Plots and summary (scripts/analyze.py → runs/<exp>/<jobid>/plots/, including summary.md)

runs/<exp>/<jobid>/plots/summary.md holds, per judged split: an overview at each split's best checkpoint, the per-checkpoint table (fully correct, mean claim coverage, material errors, truncated, judge certainty), fully correct / claim coverage / material errors per checkpoint by task_type and by category, a per-question grid sorted by task type (fully correct, else claim coverage; E = material error, T = truncated) and the reference issues from the meta file.

  • judge_eval.png: fully correct, mean claim coverage and material errors in % per checkpoint.
  • judge_eval_by_task_type.png: fully correct in % per checkpoint, separately for single-topic (implementation, 39 questions) and composition questions (9).
  • judge_<split>.png / judge_<split>_by_task_type.png for demo, oracle (and test, once judged) as well; the task-type plot needs at least two task types.
  • context_use.png: the context-use regression test (below), when eval and oracle are judged.
  • loss.png: training loss and eval loss per step (from log_history.json). Both losses cover only the answer tokens (the prompt is masked; for plain-text training rows, experiment 06, the training loss covers every token), and eval loss is computed on data/eval.alpaca.jsonl, i.e. the same 48 questions. Eval loss is shown for comparison only; checkpoints are chosen by the judge metrics.

Demo split

The 6 agent_briefing questions in data/demo.jsonl have the same schema (required/forbidden claims), so they get the same metrics (fully correct, mean claim coverage, material errors) and plots/judge_demo.png. evaluate.py and judge.py take one or more splits with --split and default to eval demo oracle; analyze.py defaults to every split that has a judgments file (eval, demo, oracle, test):

python3 scripts/evaluate.py --adapter runs/03/<jobid> --checkpoint all   # GPU node, eval + demo + oracle
python3 scripts/judge.py --run runs/03/<jobid>                           # one Claude call per split
/usr/bin/python3 scripts/analyze.py --run runs/03/<jobid>                # plots + summary.md

judge.py skips a split whose judgments_<split>.jsonl exists (pass --overwrite) and, by default, skips demo and oracle if they have no answers yet; analyze.py reports a missing eval, demo or oracle judgments file and goes on with the other splits. scripts/submit.sh runs the demo and oracle inference in the same job after the eval split, and scripts/report.sh calls judge.py and analyze.py once for all splits. With 6 questions one answer is about 17 percentage points. The briefings are long, so check the truncated column (768-token limit).

Context-use test (oracle split)

Fine-tuning on short, fixed-format answers can make an adapter recite from memory and ignore its input (experiment 05: from about one epoch on, 02 ignored paragraphs 2-4 of the input and mostly copied or recited paragraph 1). The oracle split checks this for every run. It asks the 9 eval composition questions again, with the topics' trained paragraphs in the input field, so the answer is in the prompt. judge.py grades these answers without showing the judge the input (like the closed-book eval compositions), and analyze.py compares both per checkpoint:

  • bonus = oracle minus closed-book mean claim coverage on the same 9 questions, in percentage points: how much the adapter still uses its context. Near zero or negative: it ignores the input.
  • plots/context_use.png (coverage closed vs oracle, and the bonus) and a "Context use" table in summary.md (coverage, bonus, fully correct and material errors for both).

The two splits come from separate judge calls with the same rules, and with 9 questions one claim is about 1-4 points of coverage, so read the trend over checkpoints rather than single values. The base model is not part of the standard pipeline (evaluate.py caches its answers only); experiment 05 judged it once with the oracle input: it reads the paragraphs, but runs on into a reasoning continuation and hits the token limit on every question, so it is no clean reference. For older runs, add the test with scripts/evaluate.py --adapter <run> --split oracle --checkpoint all (GPU), then scripts/report.sh <run>.

Limits

  • One judge, one call. There is no second judge, so judge noise is not measured. Rerunning judge.py --overwrite gives an estimate of it.
  • Small, correlated sample. 48 questions: one answer is about 2 percentage points, and on the 9 composition questions one answer is 11 points. Cross-topic questions share topics, so they are not independent. Treat small differences between checkpoints as noise.
  • Not independent references. The reference answers and claims were written by the same agent as the training data (see Caveats above), so the judge checks agreement with that agent, backed by the source excerpts. It is not an independent expert review.
  • Eval is development-informed. It is used to choose checkpoints and data, so its scores are optimistic. The final number for a chosen checkpoint comes from test.jsonl, run once.

Config variants

To train the same experiment (same train.jsonl) with other settings, put a full config in experiments/<NN>/configs/<name>.yaml (same format as config.yaml, e.g. an Unsloth Studio export plus model/load_in_4bit/load_in_8bit, and optionally training.text_eos: true, which appends EOS to plain-text rows, and a top-level init_adapter: runs/<exp>/<jobid>/checkpoint-<step>, which continues training that LoRA adapter instead of a fresh one, experiment 07) and pass it with --config:

scripts/submit.sh experiments/02 --config experiments/02/configs/lr2e-4.yaml [sbatch options]
scripts/report.sh runs/02/lr2e-4-<jobid>
  • The default config is experiments/<NN>/config.yaml or experiments/<NN>/configs/config.yaml (exactly one of them). The run folder is runs/<NN>/<name>-<jobid>/; with the default config it stays runs/<NN>/<jobid>/ (config name default). Names: letters, digits, ., _, -; not only digits, not default.
  • train.py prints the keys that differ from the default config and stores them in resolved_config.yaml (config_name, config_file, config_diff_vs_default); status.json also names the config. evaluate.py, judge.py and analyze.py work on the run folder as before; plot titles show 02/lr2e-4-<jobid>.
  • Each variant is a separate training run with its own judge call, so compare variants with the judge metrics, keeping the judge noise (±1–2 answers out of 48) in mind.
  • List the variants and what they change in the experiment's information.md (**configs** line).

experiment 06 format plain text (no template, no EOS, loss on every token) model Qwen03-8B bnb-4bit training set 02 without questions: per topic the recall and mechanism answers plus 7 recall and 3 mechanism rewordings (experiments/06/formulations.py), each as one {"text": ...} row (468 rows, config as 02). Tests whether training without an output format keeps the base model's context use while still teaching the facts. Config variant eos (06b, configs/eos.yaml): the same rows with an EOS token appended to each text, so answers stop instead of running to the token limit

experiment 07 format native Qwen3 chat template with thinking ({"messages": [user, assistant]} rows, scripts/chat_format.py) plus plain-text replay rows model Qwen03-8B bnb-4bit, continuing the 06 adapter (init_adapter: runs/06/241337/checkpoint-312) training set 320 rows (experiments/07/build.py, cot.py): chain-of-thought answers (recall the facts per topic in <think>, connect them, answer) for single-topic, 2–3-topic and context questions (relevant + distractor paragraphs, 6 counterfactual), only on 27 of the 39 topics, plus 78 replay texts of 06.
